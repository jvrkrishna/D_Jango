# 1. What Is a Django Application?

A Django application, commonly called an **app**, is a component inside a Django project that handles a particular area of functionality.

For example, our CampusQuest project may eventually contain:

```text
CampusQuest
│
├── accounts
├── challenges
├── leaderboard
├── submissions
├── notifications
└── core
```

Each app can contain its own:

```text
Models
Views
URLs
Templates
Forms
Admin configuration
Tests
Migrations
```

---

# 2. Project vs Application

This is one of the most important Django concepts.

## Django Project

A project represents the overall Django website/application and its configuration.

Our project is:

```text
CampusQuest
```

Its configuration package is:

```text
config
```

---

## Django Application

An app represents a particular functional area.

Examples:

```text
accounts
```

could handle:

```text
Registration
Login
Logout
Profiles
```

and:

```text
challenges
```

could handle:

```text
Challenge list
Challenge details
Challenge submissions
Challenge status
```

---

# 3. Simple Analogy

Think about a college.

The **college** is the complete organization.

Departments are individual functional areas.

```text
College
│
├── Computer Science
├── Electronics
├── Mechanical
├── Civil
└── Administration
```

In Django:

```text
Project
│
├── accounts
├── challenges
├── leaderboard
└── notifications
```

So:

```text
Project = Complete system

App = Specific functionality
```

---

# 4. A Project Can Contain Multiple Apps

A Django project is not limited to one application.

For CampusQuest:

```text
CampusQuest
│
├── accounts
├── challenges
├── leaderboard
├── submissions
└── notifications
```

This is called a **multi-app Django project**.

---

# 5. Why Do We Use Multiple Apps?

Imagine putting every feature into one application:

```text
CampusQuest
└── one gigantic app
    ├── accounts code
    ├── challenge code
    ├── leaderboard code
    ├── notification code
    └── submission code
```

As the project grows, this becomes difficult to maintain.

Instead:

```text
CampusQuest
│
├── accounts
│
├── challenges
│
├── leaderboard
│
├── submissions
│
└── notifications
```

Each app has a clear responsibility.

---

# 6. Benefits of Multiple Apps

## 6.1 Separation of Responsibilities

Each app handles a particular area.

```text
accounts
    ↓
User functionality

challenges
    ↓
Challenge functionality

leaderboard
    ↓
Ranking functionality
```

---

## 6.2 Easier Maintenance

If there is a problem with authentication:

```text
accounts/
```

is one of the first places to investigate.

---

## 6.3 Easier Team Development

Different developers can work on different apps.

```text
Developer A → accounts

Developer B → challenges

Developer C → leaderboard
```

---

## 6.4 Reusability

A well-designed Django app can potentially be reused in another project.

---

## 6.5 Scalability

As the project becomes larger, functionality can be separated into logical modules.

# 9. What Is `views.py`?

Every Django app normally contains:

```text
views.py
```

A **view** contains code that handles a web request and produces a response.

For example:

```text
Browser
   |
   | GET /hello/
   v
Django
   |
   v
View
   |
   v
Response
   |
   v
Browser
```

A view can:

- Return HTML
- Return JSON
- Read database data
- Process forms
- Perform business logic
- Return redirects
- Return API responses

---

# 10. Simple View Example

A very simple Django view can look like:

```python
from django.http import HttpResponse

def home(request):
    return HttpResponse("Welcome to CampusQuest!")
```

Don't worry about writing it yet.

We will do that in Part B.

# 11. What Is `request`?

A Django view commonly receives:

```python
request
```

Example:

```python
def home(request):
```

The `request` object contains information about the incoming HTTP request.

It can contain information such as:

```text
HTTP method
GET data
POST data
headers
cookies
user information
session information
```

---

# 12. What Is `HttpResponse`?

Django provides:

```python
HttpResponse
```

which allows a view to send a response back to the browser.

Example:

```python
return HttpResponse("Hello")
```

Conceptually:

```text
Browser
   ↓
Request

Django View
   ↓
HttpResponse

Browser
   ↓
"Hello"
```

# 14. What Is ORM?

ORM means:

> **Object Relational Mapping**

Django's ORM allows Python code to interact with database data using models.

Conceptually:

```text
Python Model
     ↓
Django ORM
     ↓
MySQL
```

For example, later we can write Python code instead of manually writing every SQL query.

# 17. What Is `tests.py`?

```text

```

is used to write automated tests.


# 18. What Is `migrations/`?

When Django creates an application, it normally creates:

```text
migrations/
```

This directory stores migration files.

Migrations help Django track changes to database structure.

For example:

```text
Model created
      ↓
Migration generated
      ↓
Migration applied
      ↓
Database structure updated
```

We will study migrations when we start working with models and databases.

# 23. Project-Level URLs vs Application-Level URLs

This is an important concept.

Our project has:

```text
config/urls.py
```

This is the **project-level URL configuration**.

Later each app can have its own:

```text
core/urls.py
```

This is the **application-level URL configuration**.

Conceptually:

```text
Project
│
└── config/urls.py
        |
        | include()
        v
      core/urls.py
```

---

# 24. Why Application-Level URLs?

Imagine CampusQuest eventually has:

```text
accounts/urls.py
challenges/urls.py
leaderboard/urls.py
```

The project can connect them:

```text
config/urls.py
       |
       +── accounts/
       |
       +── challenges/
       |
       └── leaderboard/
```

This keeps URL configuration organized.

We will implement this structure in the practical section.

# 26. What Is URL Routing?

URL routing means deciding:

> Which code should run when a particular URL is requested?

For example:

```text
/              → home view
/about/        → about view
/challenges/   → challenges view
/contact/      → contact view
```

Django uses URL patterns to perform this mapping.

# 42. Understand `core/urls.py`

This:

```python
from django.urls import path
```

imports Django's URL pattern function.

This:

```python
from . import views
```

imports the current application's `views.py`.

This:

```python
urlpatterns = [
```

contains the application's URL patterns.

This:

```python
path("", views.home, name="home"),
```

means:

```text
Empty URL
   ↓
home view
```

The empty string:

```text
""
```

represents the root of the application URL that will be included by the project.

---

# 43. Step 11 — Connect App URLs to Project URLs

Open:

```text
config/urls.py
```

Change it to:

```python
from django.contrib import admin
from django.urls import include, path


urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("core.urls")),
]
```

Save the file.

---

# 44. Understand `include()`

This line:

```python
path("", include("core.urls")),
```

means:

> Send matching URLs to `core.urls`.

The structure is:

```text
config/urls.py
       |
       v
core/urls.py
       |
       v
views.py
```
